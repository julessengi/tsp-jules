# TSP-JULES

# RFC-010 — Domain-Driven Design (DDD)

**Version :** 1.0

**Statut :** Fondatrice

**Date :** 08 Juillet 2026

---

# 1. Objet

Cette RFC définit le modèle Domain-Driven Design (DDD) de TSP-JULES.

Son objectif est d'organiser le système autour des concepts métier plutôt qu'autour des technologies.

Le domaine métier constitue la source unique de vérité.

---

# 2. Vision

TSP-JULES est une plateforme d'intelligence financière.

Le logiciel doit refléter les concepts du métier :

Observer

↓

Comprendre

↓

Décider

↓

Protéger

↓

Exécuter

↓

Apprendre

---

# 3. Domaine Principal

Core Domain

**Financial Decision Intelligence**

# 14. Anti-Corruption Layer (ACL)

Les systèmes externes ne doivent jamais polluer le domaine métier.

Des adaptateurs traduisent les données des plateformes externes.

Exemples :

Deriv Adapter

MetaTrader Adapter

REST Adapter

WebSocket Adapter

# 16. Dépendances

Les dépendances autorisées sont :

Infrastructure

↓

Application

↓

Domain

Le Domain ne dépend d'aucune technologie.

---

# 17. Gouvernance

Toute nouvelle fonctionnalité doit :

* appartenir à un Bounded Context ;
* utiliser le langage ubiquitaire ;
* respecter les agrégats ;
* publier des événements ;
* être documentée.

---

# 18. Vision d'Évolution

Le DDD permet d'ajouter :

* de nouveaux courtiers ;
* de nouvelles stratégies ;
* de nouveaux moteurs IA ;
* de nouveaux actifs ;
* de nouveaux marchés ;

sans modifier le cœur métier.

---

# 19. Conclusion

Le Domain-Driven Design constitue la structure organisationnelle de TSP-JULES.

Il garantit que l'architecture logicielle reste fidèle au métier, indépendante des technologies et capable d'évoluer sur plusieurs années sans perdre sa cohérence.

Chaque ligne de code devra exprimer clairement un concept métier défini dans cette RFC.
